# Release Pipeline Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Adopt cargo-dist 0.31.0 so pushing a `v*` tag produces a GitHub Release with macOS Apple Silicon, Linux x86_64, and Windows x86_64 binaries plus shell, PowerShell, and Homebrew installers.

**Architecture:** A declarative `dist-workspace.toml` at the repo root drives cargo-dist. Cargo-dist generates `.github/workflows/release.yml` (a ~12 KB workflow we commit verbatim and never hand-edit). A `[profile.dist]` in `Cargo.toml` tells Cargo how to build release binaries when the workflow runs. The Homebrew formula publishes into this same repo (repo-as-tap).

**Tech Stack:** cargo-dist 0.31.0, GitHub Actions, Cargo, Homebrew formula DSL.

**Spec:** `docs/superpowers/specs/2026-05-14-release-pipeline-design.md`

**Pre-flight (read once):**
- cargo-dist 0.31.0 is the version pinned in the sibling repo (`getflute/flute-webhooks`) and is the version we target. `cargo install cargo-dist --version 0.31.0` installs the CLI as `cargo dist …` and a top-level `dist` binary.
- We do not edit `.github/workflows/release.yml` by hand. If something needs to change about the workflow, change `dist-workspace.toml` and re-run `cargo dist generate`.
- Our crate has zero native deps — no apt-get step needed on Linux. Confirm by reading `Cargo.toml`: no `keyring`, no native-tls.
- The release workflow only fires on `git push` of tags matching `v*`. Pushing `main` is a no-op for CI.
- After this plan lands, **the user separately decides when to push the first `v0.1.0` tag.** Tag-pushing is explicitly out-of-scope for this plan — we just install the pipeline.

## Task 3: Write `dist-workspace.toml` by hand

We write the config file directly rather than running `cargo dist init` interactively. This is cargo-dist's documented `dist-workspace.toml` form. Hand-writing it means deterministic content, no interactive prompts, no risk of cargo-dist asking newer-version-only questions.

**Files:**
- Create: `dist-workspace.toml`

- [ ] **Step 1: Create the file**

Create `/Users/chad.lung/Rust-Projects/flute-webhooks-mcp/dist-workspace.toml` with exactly:

```toml
[workspace]
members = ["cargo:."]

# Config for 'dist'
[dist]
# The preferred dist version to use in CI (Cargo.toml SemVer syntax)
cargo-dist-version = "0.31.0"
# CI backends to support
ci = "github"
# The installers to generate for each app
installers = ["shell", "powershell", "homebrew"]
# Target platforms to build apps for (Rust target-triple syntax)
targets = ["aarch64-apple-darwin", "x86_64-unknown-linux-gnu", "x86_64-pc-windows-msvc"]
# Path that installers should place binaries in
install-path = "CARGO_HOME"
# Where to host releases
hosting = "github"
# Whether to install an updater program
install-updater = false
```

- [ ] **Step 2: Verify cargo-dist accepts the config**

Run:
```bash
cd /Users/chad.lung/Rust-Projects/flute-webhooks-mcp && cargo dist plan
```

Expected: a JSON-shaped plan printed to stdout listing the three target archives, the three installer artifacts, and the homebrew formula `flute-webhooks-mcp.rb`. Exit code 0.

If `cargo dist plan` complains about a missing field (e.g. `pr-run-mode`), copy the suggested default from cargo-dist's error message into `dist-workspace.toml` and re-run. The config above matches what 0.31.0 accepts in the sibling repo, so deviations should be small.

- [ ] **Step 3: Commit**

```bash
git add dist-workspace.toml
git commit -m "build: add cargo-dist config (3 targets, 3 installers, github hosting)"
```

## Out of scope (do not do in this plan)

- **Do not push a `v0.1.0` tag.** That is the user's call and triggers a real public release. The plan installs the pipeline only.
- **Do not edit `.github/workflows/release.yml` by hand** — even to tweak the trigger or runner choices. Anything that needs to change goes through `dist-workspace.toml` + `cargo dist generate`.
- **Do not change Cargo.toml's package version.** The first release uses whatever `version = "0.1.0"` is already declared.
