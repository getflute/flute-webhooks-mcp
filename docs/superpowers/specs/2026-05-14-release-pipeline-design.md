# flute-webhooks-mcp — release pipeline design

**Date:** 2026-05-14
**Status:** approved (brainstorm)
**Author:** chad.lung@risewithaurora.com (with Claude)

## Goal

Ship signed, pre-built binaries of `flute-webhooks-mcp` for the three
target platforms operators run Claude Desktop on, plus shell / PowerShell
/ Homebrew installers, by adopting the `cargo-dist` release pipeline.
Releases trigger only on `v*` tag pushes.

## Non-goals

- Releasing on any branch push or PR.
- Cross-compilation gymnastics — we use native runners.
- Code signing / notarization (separate effort if/when needed).
- Self-update inside the binary — covered by a follow-up spec
  (the in-app update check).

## Key decisions (from brainstorm)

| Decision | Choice |
|---|---|
| Release tooling | `cargo-dist` (matches sibling `getflute/flute-webhooks`). |
| Installers generated | shell (`*.sh`), PowerShell (`*.ps1`), Homebrew (`*.rb`). |
| Targets | `aarch64-apple-darwin`, `x86_64-unknown-linux-gnu`, `x86_64-pc-windows-msvc`. |
| Trigger | `push` of tags matching `v*`. No PR runs, no main runs. |
| Homebrew tap | This repo serves as its own tap (no separate `homebrew-*` repo). Install via `brew install getflute/flute-webhooks-mcp/flute-webhooks-mcp`. |
| Workflow filename | `.github/workflows/release.yml` (cargo-dist's default, not "build.yaml"). |
| In-app updater | Disabled (`install-updater = false`). |
| Native build deps | None — no apt-get step. Confirmed: no `keyring`, no OpenSSL crate, rustls is pulled in transitively (if at all) without system OpenSSL. |

## Architecture

`cargo-dist` is a build/release orchestrator that reads its config from
`dist-workspace.toml` (or a `[workspace.metadata.dist]` table) and
generates a GitHub Actions workflow plus a planning step that uses the
same config at runtime. Three pieces ship together:

1. **`dist-workspace.toml`** — declarative config: targets, installers,
   hosting, version of the cargo-dist tool to use in CI.
2. **`Cargo.toml`** gains a `[profile.dist]` (inherits release, adds
   `lto = "thin"`).
3. **`.github/workflows/release.yml`** — generated by `dist init`/
   `dist generate`. ~12 KB, tool-managed; never hand-edited.

### dist-workspace.toml

```toml
[workspace]
members = ["cargo:."]

[dist]
cargo-dist-version = "0.31.0"
ci = "github"
installers = ["shell", "powershell", "homebrew"]
targets = ["aarch64-apple-darwin", "x86_64-unknown-linux-gnu", "x86_64-pc-windows-msvc"]
install-path = "CARGO_HOME"
hosting = "github"
install-updater = false
```

The sibling pinned `0.31.0`; we match it for consistency. No
`[dist.dependencies.apt]` table since we have no native Linux deps.

### Cargo.toml change

Append:

```toml
[profile.dist]
inherits = "release"
lto = "thin"
```

### Workflow

`dist init` (or `dist generate`) writes `.github/workflows/release.yml`.
Its essential shape:

- Triggers: `on: { push: { tags: ['v*'] }, workflow_dispatch: {} }`.
- `plan` job: runs `dist plan` to compute the artifact list for this
  tag (deterministic from the version + config).
- Matrix `build-binaries` job: one entry per target on the matching
  runner (`macos-latest` → ARM, `ubuntu-latest`, `windows-latest`).
  Runs `dist build --tag $TAG --target <triple>`.
- `build-global-artifacts` job: produces the cross-cutting artifacts
  (installer scripts, Homebrew formula, checksums sidecar).
- `host` job: creates/updates the GitHub Release for the tag, uploads
  all artifacts, and (since Homebrew is in the installer set) commits
  the `.rb` formula back into this same repo at the tag SHA.

## Install surface after release

```bash
# macOS / Linux
curl -LsSf https://github.com/getflute/flute-webhooks-mcp/releases/latest/download/flute-webhooks-mcp-installer.sh | sh

# Homebrew (repo-as-tap)
brew install getflute/flute-webhooks-mcp/flute-webhooks-mcp

# Windows
powershell -c "irm https://github.com/getflute/flute-webhooks-mcp/releases/latest/download/flute-webhooks-mcp-installer.ps1 | iex"
```

## Trigger semantics in detail

| Event | Result |
|---|---|
| `git push origin v0.1.0` | Full release workflow runs; archives + installers + Homebrew formula uploaded; release published. |
| `git push origin v0.1.0-rc1` | Same. cargo-dist treats it as a prerelease. |
| `git push` (no tag) | Workflow does not run. |
| PR opened | Workflow does not run. |
| Manual `workflow_dispatch` | Allowed (cargo-dist generates this entry too). Useful for re-running a failed release without retagging. |

## Generation method

We run `cargo-dist` locally to produce the files (rather than
hand-writing the workflow YAML):

1. `cargo install cargo-dist --version 0.31.0`
2. `cargo dist init` — interactive. Answer:
   - `ci = github`
   - `installers = shell, powershell, homebrew`
   - `targets = aarch64-apple-darwin, x86_64-unknown-linux-gnu, x86_64-pc-windows-msvc`
   - `hosting = github`
   - `install-updater = no`
   Alternatively, write `dist-workspace.toml` by hand with the contents
   shown above and run `cargo dist generate` to produce the workflow
   non-interactively.
3. Commit the resulting `dist-workspace.toml`, `Cargo.toml` profile change,
   and `.github/workflows/release.yml`.

After that, any future change to the release config (new targets, new
installers) follows the same flow: edit `dist-workspace.toml`, run
`dist generate`, commit.

## Verification

1. `cargo dist plan` locally — must succeed and print a manifest matching
   the table above.
2. `cargo build --release` still succeeds (no toolchain regression).
3. `cargo test --all-targets` still green.
4. After a `v0.1.0` tag push, the GitHub Actions run reaches "host"
   without error and the release page lists every artifact in the
   table above.
5. The Homebrew formula file `flute-webhooks-mcp.rb` is committed to
   the repo at the tag SHA.

## Out of scope (follow-up)

- **In-app update check.** A separate spec covers checking GitHub
  Releases at most once per 24 h, caching the result, surfacing
  "newer version available" to operators via stderr at startup and to
  agents via a new `mcp_status` tool. That work depends on this
  release pipeline existing (so there's a real "latest release" API
  endpoint to query).
- Code signing for macOS / Windows.
- A separate `homebrew-<tap>` repo (we use repo-as-tap for now).
